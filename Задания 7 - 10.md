## **Варианты шардирования**


Заказы шардировать по зоне для ускореня работы логистики `sh.shardCollection("somedb.orders", { area: 1, _id: 1})`, а для поиска по пользователю добавить индекс `db.products.createIndex({ user_id: 1, order_date: -1 })`


Товары для быстрого поиска предлагаю шардировать через хеширование id, чтобы равномерно распределять данные. `sh.shardCollection("somedb.products", { _id: "hashed"})` а для поиска добавить индексы `db.products.createIndex({ category: 1, current_price: 1 } )`

Корзину предлагаю шардировать отдельно вычисляемым ключем, который будет получаться из хеша user_id, а если его нет, через хеш сессии, чтобы можно было хранить корзины пользователя на одном шарде. `sh.shardCollection("somedb.carts", { shard_key: 1 })`


## Выявление и устранение «горячих» шардов

Для определения горячих шардов предлагаю использовать такие метрики: распределение данных, количество операций, производительность.

На роутере можно посмотреть в mongosh метрики по распределению данных через команду `sh.status();`
Командой `db.serverStatus().opcounters;` можно посмотреть счетчики операций
Скорость ответа можно узнать командой `db.serverStatus().opLatencies;`

При выявлении проблем может потребоваться добавление индексов. Это делается через команду `db.<your_collection>.createIndex({<attribute_name>: <direction>})`. Возможно потребуется перебалансировка `sh.moveChunk()`

 ## Миграция на Cassandra: модель данных, стратегии репликации и шардирования

 ### Определение критичных данных

Критически важными с точки зрения целостности и скорости обработки являются заказы и товары, в основном в области списания остатков. Поэтому я бы оставил эти данные в mongodb. 

Кандидаты на вынос в C* это пользовательские сессии (потому что при наплыве пользователей нужно быстро масштабировать систему благодаря consistent hashing) и историю/статусы заказов пользователя (в C* данные сразу хранятся с timestamp), удобно будет получать историю. Так же в Cassandra я бы вынес все пользовательские действия, потому что действий очень много как в IoT и высокая скорость записи важнее возможной несогласованности в моменте, и действия используются для аналитики, здесь происходит write once read many

### Концептуальная модель 
```
CREATE TABLE clickstream_events (
    -- Такой partition key гарантирует, что все события конкретного пользователя за день находятся в одной партиции
    bucket_date TEXT,
    user_id UUID,

    -- Clustering ключи позволят отсортировать данные по времени по убыванию
    event_time TIMESTAMP,
    event_id TIMEUUID,

    event_type TEXT, -- 'view_product', 'search', 'add_to_cart'
    product_id UUID,
    page_url TEXT,

    PRIMARY KEY ((bucket_date, user_id), event_time, event_id)
) WITH CLUSTERING ORDER BY (event_time DESC, event_id DESC);
```

```
CREATE TABLE user_sessions (
    -- Partition Key
    session_id UUID,
    user_id UUID,
    session_data TEXT, -- JSON blob или конкретные поля
    created_at TIMESTAMP,
    last_activity TIMESTAMP,
    -- PRIMARY KEY
    PRIMARY KEY ((session_id))
) WITH default_time_to_live = 3600; -- Автоудаление через час неактивности (TTL)
```

Про решардинг. При добавлении новых нод в Cassandra данные не перераспределяются массово, а значит каждая нода становится ответственной за новый диапазон хэш-ключей. Старые данные остаются на местах, новый трафик начинает распределяться на новую ноду. Это исключает просадки latency, как в MongoDB.

###  Стратегия обеспечения целостности данных

Для всех сущностей работает механизм Hinted Handoff.

Для сессий выбираем более высокий уровень гарантии согласованности за счет небольшого увеличения latency на чтение (Read Repair). Для событий выбираем максимальную производительность и доступность записи/чтения, полагаясь на фоновый Anti-Entropy Repair для долгосрочной целостности.
